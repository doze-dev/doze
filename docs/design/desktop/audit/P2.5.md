# P2.5 audit: domains, https, `doze trust`

Independent review, 2026-11-05. Basis: doze `5b45cc3`; doze-names `32e19ae`
(a third commit, "forget a dropped domain that was never routed; test the
forward", landed at 13:05 while this audit ran, after the brief named
`d9bc47c`; audited as it stands). Both trees clean. Nothing was changed.

Gates pass (section 6). The feature's shape matches the plan; the parts the
plan called "the one piece of real new resolver logic" and "the trust-store
matrix" are where it breaks. Ranked, most severe first.

## 1. Blocking

**B1. `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` replace the trust store, so
the stack's own processes can no longer reach any public https host.**
`internal/daemon/ingress.go:117-124`, `internal/runtime/runtime.go:1183-1197`.
`NODE_EXTRA_CA_CERTS` is additive; the other two are not. For OpenSSL-based
clients (Python `ssl`/`requests`/`httpx`/aiohttp, Ruby, PHP, Linux curl and
Go) the doze root becomes the *only* trusted root. Scenario: the exact use
case the feature exists for — a Flask or Django app does Google sign-in;
the browser leg works, then the server exchanges the code at
`https://oauth2.googleapis.com/token` with `requests` → `CERTIFICATE_VERIFY_FAILED`.
Any Stripe/Twilio/npm-registry call from a process doze runs fails the same
way. Also: `exec.Cmd` keeps the *last* duplicate key, so a person's own
`SSL_CERT_FILE` (corporate proxy CA) is silently overridden. mkcert and
OrbStack deliberately do not set these. Fix: ship a bundle (system roots +
doze root, as mkcert's docs describe for Python) or set only
`NODE_EXTRA_CA_CERTS` + `DOZE_CA_FILE` and document the rest.

**B2. Linux: the route drop-in replaces the link's domain list, so after a
reboot only the last domain is routed and `~doze` is gone.**
`doze-names/trust_linux.go:30-36`, `setup_linux.go:62`. `resolvectl domain
LINK DOMAIN…` *sets* the list. The zone unit runs `resolvectl domain doze0
~doze`; `domains.conf` appends `ExecStart=-/usr/bin/resolvectl domain doze0
~dev.acme.com` (just the new one, despite the comment "restates the whole
set"). Scenario: declare one domain, `doze trust`, reboot → `.doze` names
stop resolving; declare two → only the second works. Linux is unpublished,
but the script is in the tree and `doze trust` runs it.

## 2. Should fix — security and honesty of the model

**S1. The sudo prompt, `--help` and the docs say the CA "can sign only
names declared on this machine". It cannot be constrained and is not.**
`doze-names/trust.go:76`, `cmd/doze/trust.go:28-29`,
`website/.../domains.md` ("What the authority is"); `ca.go:103-116` has no
`PermittedDNSDomains`. The plan chose no name constraints (fine, same as
mkcert) and said "the dialog says exactly what the CA can and cannot do".
The dialog says the opposite. Whoever copies `root.key` can mint
`accounts.google.com` and this machine will trust it. Say so.

**S2. `--rotate` leaves the old root trusted and destroys the only record
of its fingerprint; `--remove` can only ever delete the root on disk.**
`cmd/doze/trust.go:52-58`, `ca.go:139-154`, `trust_darwin.go:56-58`.
Rotation is the remedy the plan offers for a copied key; after it the
copied key is still a trusted root in the System keychain, forever, with
no doze command able to remove it (Linux is fine: `cp -f` overwrites).
`delete-certificate` also lacks `-t` (orphaned trust settings). Fix: keep
trusted fingerprints in `ca/`, untrust the old root in the rotate prompt,
and enumerate by `-c "doze local CA"` on remove.

**S3. `doze dns-setup --uninstall` leaves `/etc/resolver/<domain>` files
pointing at a port nothing will serve again, and the CA trusted.**
`doze-names/setup_darwin.go:175-189` removes only `resolverFile`. The docs
say it "takes everything away". Scenario: uninstall doze; `dev.acme.com`
(a real staging host) is unresolvable on this Mac until someone finds
`/etc/resolver` by hand.

**S4. Nothing serves the resolver when no stack runs, so a declared real
domain is dead the moment doze is fully down.** `upstream.go:14-21`
promises the internet's answer; it only holds while *some* daemon holds
`:5323`. `netd` does not serve DNS. macOS does not fall back when the
drop-in's server refuses UDP. The docs' "When no stack is running, the
resolver forwards the name to your usual DNS" is false; the plan's table
row says the same. Either serve the resolver from `netd`/launchd, or
document "while any doze stack runs".

**S5. `routes.json` keys are fed to `sudo sh` with no `ValidDomain` check;
on Linux they sit inside single quotes.** `routes.go:24-30`,
`trust.go:65-67`, `trust_linux.go:38-42`. The file is user-writable (any
npm postinstall can write it). The `StaleRoutes` gate requires
`"~"+key` to appear in `resolvectl` output, which an empty key satisfies:
`sed 's/~//'` then strips every routing marker and turns `~doze
~dev.acme.com` into search domains. macOS is `shellQuote`d and safe.
Validate on read; `ValidDomain` itself is sound (`label()` rejects every
byte outside `[a-z0-9-]`, trailing/leading dashes, empty labels).

**S6. The https redirect runs before `fromThisMachine`, and the TLS
handshake serves leafs to any LAN peer.** `ingress.go` `withHTTPSRedirect`
wraps `proxy`; `GetCertificate` has no peer check. A LAN host learns which
domains this laptop serves (307 vs 403; cert vs alert). The `:80` comment
promised "a refused peer also learns nothing". Minor leak, easy fix (check
the peer in the wrapper; `GetConfigForClient` for 443).

## 3. Should fix — correctness

**C1. A wildcard-only declaration points every surface at a name doze does
not serve.** `domains = ["*.dev.acme.com"]` → `endpoints.go:64-72` picks
`https://dev.acme.com` for `doze url`, the Connect card and ⌘K;
`lookupDomain` (`domains.go:78-93`) does not match the base name for a
wildcard, so the resolver forwards it upstream and the front door 404s —
while `mint` (`ca.go:251-254`) puts the base name in the SAN, as if it
were meant to be served. Three layers disagree. Related: a depth-2 name
(`a.b.dev.acme.com`) resolves, routes and is redirected to https, then
fails the one-label certificate; only a code comment says so, the docs do
not. `ownerOf` duplicates the walk; one function returning (entry, owner)
removes the drift.

**C2. A held twin is logged and then forgotten.** `daemon/domains.go:120-123`
calls `noteHeld`, which matches only `DomainFor(decl)` or the aws host
(`:92-105`), never `dev.acme.com`. Two stacks declaring one domain: the
second runs, `doze status`/`doctor` show nothing, and the plan promised a
refusal "like a .doze collision".

**C3. Bare and third-party suffixes pass validation.** `ValidDomain`
accepts `*.co.uk`, `*.github.io`, `*.google.com` (`domains.go:57`); `doze
trust` then writes `/etc/resolver/google.com` and hijacks it for the
machine while the stack is up. Plan: "Not allowed: a bare public suffix".
`publicsuffix.EffectiveTLDPlusOne(RouteDomain(d))` erroring is the test
(verified: `co.uk` errors, `acme.co.uk` passes). The doctor line
(`doctor.go:313-315`) misfires the other way: `foo.github.io` is flagged
"not under a public TLD" because `icann` is false for the private section.

**C4. CA creation races and self-rotates silently.** `ca.go:61-74`: two
daemons starting on a fresh home (the app's remembered "Up" set) both
`create()`; the loser holds `:443` with a root that is not on disk, so
`doze trust` trusts the wrong one until a restart. The same function
re-creates on any unparsable file, from read-only surfaces: `doctor.go:331`,
`up.go:319`, `trust.go:48` use `LoadOrCreateCA`, not the `OpenCA` added for
them. Take the registry lock around create and re-load after.

**C5. CA env reaches specs and their hooks only.** Tasks
(`runtime/tasks.go:162-163`) and setup/on_ready/stop steps
(`steps.go:72-73`) spawn with their own `Env`; `doze env` (`cmd/doze/env.go`)
emits nothing. Docs: "on every process it runs"; plan: "`doze env` … carry
`DOZE_CA_FILE`". A `migrate` task calling the app over https fails. (Fix
together with B1.)

**C6. The desk runs `security find-certificate` on every home push.**
`serve/service.go:222-226` → `setupFor` (`:316-340`) → `TrustStatus` →
exec per push (one per `Pace` tick while anything changes), for as long as
a stack with domains is focused, even once everything is trusted. Against
D14. Cache with a TTL, or compute on focus change and after `trust`.

**C7. `routes.json` has no lock.** `routes.go:24-41, 45-63`: read-modify-
write, and `writeFileAtomic` uses one fixed `.tmp` name. Two daemons
starting together lose one project's record; the lost domain is then
never reported stale and `--remove` for that project does nothing. The
registry next to it already uses `flock`.

**C8. `--remove` edge logic.** `cmd/doze/trust.go:68-83`: `ForgetProject`
runs before `--print` (mutates the record without removing anything);
`len(Recorded) > len(Stale)` keeps the CA trusted when one of this
project's own domains was never routed, silently; `--rotate --remove`
rotates first and then deletes the *new* fingerprint; when there is nothing
to do `Untrust` returns with no output; CA files are never deleted (plan:
"undoes everything (…CA files)").

## 4. Minor

- `own()` drops `127.0.0.1` upstreams (`upstream.go:60-66`): a Mac with
  dnscrypt-proxy, NextDNS CLI, Pi-hole or dnsmasq on `127.0.0.1:53` has no
  upstream, so a declared-but-down domain gets NXDOMAIN. Only `127.0.0.53`
  (resolved's stub) can loop. The resolver is also an open forwarder for
  anything that reaches `:5323` (on Linux, `192.0.2.53` is reachable from
  containers).
- `add-trusted-cert` without `-p ssl -p basic` trusts the root for code
  signing and S/MIME too (`trust_darwin.go:53`).
- Linux `unrouteScript` sed uses unescaped dots and prefix matching:
  removing `dev.acme.com` corrupts `~dev.acme.community`
  (`trust_linux.go:39-40`); `domainRouted` is a substring test (`:24`).
- Windows: `routeScript` returns `""` and `Trust` still runs `sudo sh` on
  blank lines (`trust.go:53-58`, `trust_windows.go`).
- The daemon creates a CA even when every domain brings its own files
  (`daemon/ingress.go:40-44`); docs say "trusts nothing of its own".
- `doze url` and the Connect row show `https://…` whatever the front door
  and trust state (`verbs.go:528`, `view/instance.go:302`); the plan said
  Go computes it "from the registry's routes and the CA state". Doctor's
  `:443` line does not name the holder (`doctor.go:343-347`) though the
  plan shows "held by caddy pid 1234". The home table's URL column is
  unchanged (plan: shows the domain).
- `Trust()` computes `steps` and discards it (`trust.go:50, 73`); the sudo
  message mentions trusting the CA even when only routes are missing.
- A `service` block with `domains` gets HCL's generic "not expected", not
  the written message at `config/domains.go:99-101` (only modules reach it).
- `IsDomain` adds a second registry read per plain request (`domains.go:97-106`).

Checked and fine: port 443 binds unprivileged on macOS ≥10.14 and on Linux
under the existing `ip_unprivileged_port_start=80`; key `0600` in a `0700`
folder; no-SNI and IP-SNI handshakes fail closed; the redirect host is
limited to registered names (no open redirect); `.doze` queries are never
forwarded and the forward runs off the serve loop; `SetXForwarded` gives
the app `X-Forwarded-Proto: https`; `--print` output is a quoted heredoc so
the single quotes inside paste correctly; twins are released at shutdown and
by `republishDomains` on a live remove; `Certificate()` is re-applied after
every re-claim; `CheckSignatureFrom` guards the on-disk leaf cache; leaf
renewal at <7 days does not disturb open connections.

## 5. Tests

Vacuous: `TestRoutesRememberWhoAskedAndGoStaleWithTheConfig` never produces a
stale route — `domainRouted` is platform code with no seam, so the test
asserts `len(stale) == 0` and the central promise (dropped domain → stale →
pruned) is unexercised. `TestValidDomain…` has no shell-metacharacter or
`..`/`/` cases, which is the property the sudo script depends on.

Untested: every trust/untrust script (content, quoting, idempotence);
`caTrusted` and `scutilResolvers` parsing; leaf renewal near expiry;
`LoadOrCreateCA`'s re-create path and `OpenCA`; wildcard-only base-name and
depth-2 behaviour; `withExtraEnv`/`SetExtraEnv`/`caEnv` (no runtime test);
`claimAppDomains` and twin release on live remove (no daemon test);
`noteHeld` for a domain; `domainChecks`, `trustHint`, `trustCmd` flags;
`endpoints` HTTPS selection; `setupFor`; `RecordDomains` under concurrency.
The desk e2e spec exists but was not run here.

## Resolution (2026-11-05, after the audit)

Fixed, in doze-names 0039dce.. and the doze commit after 5b45cc3:

- B1: `SSL_CERT_FILE` and `REQUESTS_CA_BUNDLE` point at `ca/bundle.pem`, the
  machine's roots (and any `SSL_CERT_FILE` the daemon inherited) plus the
  doze root; `NODE_EXTRA_CA_CERTS` and `DOZE_CA_FILE` stay the root. Verified
  on a real stack: `curl --cacert bundle.pem https://example.com` → 200 and
  the domain verifies through the same file.
- B2: routes are restated whole; Linux writes the link's full domain list
  (`~doze` and every route) at runtime and in the drop-in.
- S1: the prompt, `--help` and the docs say the authority could sign any
  name and that its key stays in `~/.doze/ca`.
- S2: rotated-out fingerprints are kept (`ca/previous.json`) and untrusted in
  the next prompt; untrust uses `-t`; `--rotate --remove` is refused.
- S3: `dns-setup --uninstall` removes every recorded route, the authority's
  trust and files, and the record.
- S4: documented honestly: forwarding holds while any doze daemon serves the
  resolver; with doze fully down the route points at nothing on macOS.
  Serving the resolver from netd is an open item.
- S5: record keys are validated on read; the Linux script no longer uses
  sed or grep on domain names.
- S6: the peer is checked before the https redirect and in the handshake.
- C1: a wildcard owns the name under it (one walk, one owner); depth-2
  names are documented as resolving but failing the certificate.
- C2: a domain held by another stack is recorded against the app
  (`noteHeld`), so status and doctor show it.
- C3: a bare public suffix is refused in config; doctor warns only when the
  top-level domain is unknown to the public suffix list.
- C4: authority creation is locked; an unreadable authority is an error,
  never replaced; reporting surfaces use `OpenCA`.
- C5: tasks and setup steps get the environment; `doze env` prints it.
- C6: the app caches the trust check for a minute.
- C7: the record is written under a lock.
- C8: `--remove` changes nothing under `--print`, removes only routes no
  other project declares, and takes the authority's trust and files with the
  last project.
- Minor: local loopback upstreams kept (only the resolved stub and the zone
  address are excluded); forwarding only for this machine's queries;
  `-p ssl -p basic`; the authority is made only when a domain is minted;
  doctor names what holds :443; Windows returns an error instead of running
  an empty script.

Still open: the resolver with doze fully down (netd), the home table's URL
column, the `doze url` line not reflecting the trust state, the Linux
scripts untested on Linux, the Google redirect check, the runtime's extra
environment reaching module engines (it does, harmlessly).
