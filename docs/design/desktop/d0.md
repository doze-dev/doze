# D0: platform proof

Started 2026-11-02. These are the checks that decide whether the plan holds:
one binary (CLI, app and daemon) built without cgo, on macOS and Linux.

## Results so far

### A Wails-linked binary on a Linux server: works

A binary that links `wails/v3/pkg/application` (v3.1.0, `-tags purego`,
`CGO_ENABLED=0`, linux/arm64) runs on Debian 12 with no GTK or WebKitGTK
installed. It exits 0 and maps no GUI library.

| On Linux, no GUI libraries | RSS |
|---|---|
| plain Go binary | 2.0 MB |
| Wails linked, never used | 6.9 MB |

### On a Linux desktop, Wails costs every process: lazy loading fixes it

With GTK4 and WebKitGTK 6.0 installed (Ubuntu 24.04), stock Wails loads them
in a package `init()` (`linux_purego.go:34`), so every process that links the
package maps them: each CLI call, and the daemon.

| Ubuntu 24.04, GTK4 + WebKitGTK installed | RSS | GUI libraries mapped | Time to run and exit |
|---|---|---|---|
| plain Go binary | 2.0 MB | 0 | 1.3 ms |
| Wails, stock | 36.8 MB | 8 | 20.4 ms |
| Wails, libraries loaded lazily | 6.9 MB | 0 | 4.0 ms |

Stock Wails would break the daemon's memory budget by about 30 MB and the CLI's
15 ms target on every Linux desktop. The patch, prototyped in a local copy:

- `linux_purego.go`: the `init()` becomes `ensureLinuxLibraries()`, a
  `sync.Once` that loads the libraries and records the main thread.
- `application.go`: `New` calls a `platformInit()` first. It loads the
  libraries on Linux purego and does nothing elsewhere
  (`platform_init_other.go`).
- It is safe because `init_desktop.go` locks the main goroutine to the startup
  thread, so `New`, called from it, is still on the thread GTK runs on.

To ship: a fork carrying this patch through a `replace`, and the same change
offered upstream. The upstream pull request needs Srini's go-ahead: it is
public, under his account, to a third-party project.

### A Wails window on Linux in a container: not yet run

A minimal app (one window, one page that emits an event and quits) crashed
inside an Ubuntu 24.04 container under Xvfb, both with stock Wails and with
the patch, and with a cgo build too. The cause is the container, not Wails:
WebKitGTK sandboxes its web process with bubblewrap, which cannot create
namespaces in an unprivileged container, and GLib aborts
(`Failed to fully launch dbus-proxy`, then SIGTRAP).

Running it needs one of:
- the container with WebKit's sandbox turned off (test-only), or
- a GitHub Actions Linux runner, or
- a real Linux desktop.

**Note for shipping:** Ubuntu 24.04 restricts unprivileged user namespaces
through AppArmor, which can stop WebKitGTK's sandbox the same way. The deb and
AppImage may need an AppArmor profile; D0 has to check this on a real
Ubuntu 24.04 desktop.
