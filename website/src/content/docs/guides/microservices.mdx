You'll be able to run ten services of your own, in three languages, with their
databases, migrations and installs, started in the right order by one command.

:::note
The example is **Larder**, a made-up grocery delivery service. It is not a real
shop; it exists so every page shows the same stack. Its `doze.hcl` is in
[doze-examples/larder](https://github.com/doze-dev/doze-examples/tree/main/larder).
:::

## What Larder runs

| Kind | Blocks | Language |
|---|---|---|
| Apps with a port | `identity`, `catalog`, `orders`, `payments`, `gateway` | Go |
| | `fulfilment`, `recommendations` | Python, with uv |
| | `storefront` | TypeScript, Vite on bun |
| An app with no port | `notifications` | TypeScript on bun |
| Shared services | `postgres`, `redis` (Valkey), `kafka`, `aws` | modules from the registry |
| Your own service | `mailpit` | a download, pinned in `doze.lock` |
| Tasks | `migrate-*`, `install-*`, `seed-catalog` | run before the apps that need them |

Every app is a native process on your machine: your debugger attaches to it,
and `go run`, `uv run` and `bun --watch` reload the way they do in a terminal.

## One app, read line by line

```hcl
app "catalog" {
  run   = "go run ./services/catalog"
  watch = ["services/catalog/**/*.go", "platform/**/*.go"]
  port  = 8002
  ready = http("/healthz")
  after = [task.migrate-catalog]

  env = {
    DATABASE_URL     = "postgres://catalog:catalog@${module.postgres.address}/postgres?sslmode=disable"
    AWS_ENDPOINT_URL = module.aws.url
    IMAGES_BUCKET    = "product-images"
  }
}
```

- `run` is the command, run through `sh -c` from the folder `doze.hcl` is in
  (or from `dir`, if you set one).
- `port` is where other services reach it. doze holds that port and starts the
  app with `$PORT` set to a private one, so the app must listen on `$PORT`.
  That is how a sleeping app wakes on its first request. See
  [Apps](/hcl/apps/).
- `ready` says when the app is ready: here, when `/healthz` answers. Anything
  that waits on `catalog` waits for that, not for the process to exist.
- `after` lists what must happen first. `task.migrate-catalog` runs before
  `catalog` starts.
- `env` can point at other blocks. `module.postgres.address` and
  `module.aws.url` are filled in by doze, and each reference is also an order:
  `catalog` waits for `postgres` and `aws` to be ready.
- `watch` restarts the app when those files change.

The same block shape works for every language. Only `run` changes:

```hcl
app "fulfilment" {
  dir   = "services/fulfilment"
  run   = "uv run --frozen python -m fulfilment"
  port  = 8005
  ready = http("/healthz")
  after = [task.install-fulfilment]
}

app "storefront" {
  dir   = "apps/storefront"
  run   = "bun run dev"
  port  = 5173
  ready = http("/")
  after = [task.install-storefront]
  env   = { GATEWAY_URL = app.gateway.url }
}
```

A Vite dev server takes its port from its own config, so Larder's
`vite.config.ts` reads `PORT` (and `HOST`) from the environment, with
`strictPort: true`. An app that listens on a
port of its own instead of `$PORT` is never ready; see
[Troubleshooting](/guides/troubleshooting/#an-app-is-never-ready).

## Workers with no port

`notifications` reads Kafka and sends email. Nothing calls it, so it has no
`port`, and its `ready` is a line in its own output:

```hcl
app "notifications" {
  dir   = "services/notifications"
  run   = "bun src/index.ts"
  ready = log("consuming")
  after = [task.install-notifications]

  env = {
    KAFKA_BROKERS = module.kafka.address
    SMTP_ADDR     = service.mailpit.address
  }
}
```

An app with no port runs until you stop it. An app with a port sleeps after
two minutes with no connections and wakes on the next request. A consumer
gets its work from Kafka, not from requests, so nothing would ever wake it.
Larder keeps those awake:

```hcl
app "orders" {
  run   = "go run ./services/orders"
  port  = 8003
  sleep = "never" # it consumes Kafka: no request would ever wake it
}
```

More in [Sleep and wake](/hcl/sleep/).

## Migrations and installs are tasks

A `task` runs to the end and stops. An app that lists it in `after` waits for
it to succeed. With `inputs`, it runs again only when those files change:

```hcl
task "migrate-catalog" {
  run    = "go run ./platform/cmd/migrate services/catalog/migrations"
  inputs = ["services/catalog/migrations/*.sql"]
  env    = { DATABASE_URL = "postgres://catalog:catalog@${module.postgres.address}/postgres?sslmode=disable" }
}

task "install-fulfilment" {
  dir    = "services/fulfilment"
  run    = "uv sync --frozen"
  inputs = ["pyproject.toml", "uv.lock"]
}

# Only when asked.
task "seed-catalog" {
  run    = "go run ./platform/cmd/migrate services/catalog/seed"
  manual = true
  after  = [task.migrate-catalog]
  env    = { DATABASE_URL = "postgres://catalog:catalog@${module.postgres.address}/postgres?sslmode=disable" }
}
```

Each Larder service migrates its own schema as its own Postgres role, so one
service cannot touch another's tables. The roles and schemas are declared on
the `postgres` module. See [Tasks](/hcl/tasks/) and
[Start order and readiness](/hcl/start-order/).

A `manual = true` task never runs by itself. Run it when you want it:

## Bring it up

To work on two services, start only those: `doze up storefront gateway`
starts them and everything they reference. In the app, while the stack is
down, the `…` menu beside its switch has **Choose what starts…**. Next time, `doze up` asks whether to
start the same set again.

## Run a test against the stack

`doze run` makes sure the stack's daemon is up, then runs your command. With
`--env` it also sets the connection variables that `doze env` prints, such as
`DATABASE_URL`:

```sh
doze run --env -- go test ./...
```

Without `--env` nothing is added to the command's environment. Larder's apps
get their variables from their own `env` blocks, so they need neither.

## Keep the data somewhere else

You don't have to run the databases. If your team shares a database on a
server, leave the module out and put its address in `env`. doze runs and
orders your services; the database is just a string to it:

```hcl
app "catalog" {
  run   = "go run ./services/catalog"
  port  = 8002
  ready = http("/healthz")

  env = {
    DATABASE_URL = "postgres://catalog@db.dev.internal:5432/larder"
  }
}
```

Mix the two as you like: a local Postgres and a shared Kafka, or the
reverse. Only blocks are started, ordered and woken.

## Anything not in the registry

Larder catches email with mailpit, which is not a doze module. It runs as a
`service` that doze downloads once and pins in `doze.lock`. See
[Your own services](/hcl/your-own-services/).
